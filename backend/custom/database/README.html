执行方式

# 首次准备 CRMEB 后，执行迁移、通用种子、校验和状态输出
./scripts/manage-local-database.sh setup

# 日常查看迁移版本、表数量和租户/渠道数量
./scripts/manage-local-database.sh status

# 可独立执行的阶段
./scripts/manage-local-database.sh migrate
./scripts/manage-local-database.sh seed
./scripts/manage-local-database.sh verify

setup 先确认每个 *.up.sql 都有同版本 *.verify.sql，再按文件名顺序执行迁移。新迁移只有在结构验证通过后，才把版本、SHA-256 校验和与执行时间写入 ch_schema_migration；验证失败会保留未登记状态，修复结构后可安全重跑。

已登记迁移不会只做跳过：脚本先核对历史校验和，再重新运行对应结构验证，用于发现缺表、缺列、关键类型变化、索引缺失等常见漂移。独立执行 verify 会同时复验全部迁移结构和本地种子；若结构完整但版本未登记，会明确要求执行 migrate 完成登记。

当前本地基线为 CRMEB 157 张原表、21 张商会领域/可靠性表和 1 张迁移登记表，共 179 张。四个迁移验证器合计 394 项结构复验，其中 G0 为 165 项，G1 的 003/004 为 158 + 71 = 229 项。MySQL DDL 会自动提交，发布时先执行迁移再切换应用版本；生产环境不得执行通用种子或 down.sql。后续变更必须新增迁移文件，不回写已登记的迁移，也不修改 CRMEB 的 public/install/crmeb.sql。

本地与 CI 种子边界

种子创建 local-primary、local-secondary 两个不绑定真实品牌的通用租户；每个租户只创建一个 default 渠道，以及普通会员、导师、教练、行业领袖四个角色。

  • 不创建 CRMEB 用户、租户会员、活动、商品、订单或其他业务内容。
  • 重复执行只插入缺少的唯一键，不更新、启用或恢复已有记录。
  • 若基线记录已被停用或软删除，校验结果会显示 FAIL，由开发者明确处理，不由种子覆盖配置。
  • 该种子不得在生产环境执行，生产租户必须通过受控初始化流程创建。
  • 校验 SQL 第一份结果集应为三行 PASS，第二份结果集应为八条租户角色明细。

  • 租户与运营组织：ch_tenant、ch_channel。
  • 会员与认证：ch_tenant_member、ch_member_profile、ch_graduate_verification、ch_audit_record。
  • 人物角色：ch_persona_role、ch_role_application、ch_member_role。
  • 活动报名：ch_event、ch_event_ticket、ch_event_registration、ch_event_checkin。
  • 商业事件可靠性：ch_commerce_event_inbox、ch_idempotency_record、ch_refund_attempt。

好友关系、积分/贡献账本、商品审核、分账、大咖预约和 AI 账本不属于当前迁移，待对应服务契约确认后分批追加。

商业事件与退款契约

  • ch_commerce_event_inbox 只接收最小化、脱敏后的商业事件。禁止写入姓名、手机号、邮箱、地址、OpenID、证件号或未经筛选的渠道原始报文。
  • event_id 是由 tenant_id + source + event_type + source_event_id + schema_version 生成的确定性 SHA-256 全局事件标识；tenant_id + source + event_type + source_event_id 同时保持来源唯一。重复事件命中唯一键后，服务必须比较 payload_hash：同哈希返回已有结果，异哈希标记冲突并告警，禁止覆盖原载荷。
  • channel_id、order_pk/order_no、business_type/context_id 和 correlation_id 是公共非 PII 运维上下文。订单与领域上下文必须写入这些结构化列，不能只埋在 payload_json。
  • ch_idempotency_record 的数据库唯一身份是 tenant_id + internal_idempotency_key：服务端把版本号、稳定 operationId、可信认证主体类型/ID 与客户端 Idempotency-Key 组成规范化元组并计算 SHA-256，结果写入现有 idempotency_key 列。禁止把客户端原始键直接作为数据库身份；首次执行方持有有期限的 lease_token，同内部键仅在请求哈希一致时重放，异哈希返回冲突。
  • ch_refund_attempt 必须在调用支付渠道前持久化 refund_no 和 provider_refund_no。网络超时进入 unknown，由同一退款号查询恢复，不得生成新号盲目重试。
  • 退款状态只允许按服务状态机使用 requested / processing / succeeded / failed / unknown / manual。manual 表示等待线下凭证和人工确认，不等于成功。
  • 只有余额退款事务提交、主动查询确认渠道成功或人工财务复核产生最终证据后，才能设置 final_confirmed=1；对应 final_confirm_source 只能是 balance_transaction、provider_query_success 或 manual_finance_confirm。渠道同步受理和 CRMEB 本地退款状态都不能作为完成证据。

实现约束

  • eb_user 仍是全局登录账号，ch_tenant_member 是租户内身份；禁止同步覆盖两者的业务含义。
  • 除租户根表外，每张私域表都带 tenant_id，Dao 查询仍必须由 TenantContext 强制注入范围。
  • 不使用数据库外键，保持 CRMEB 现有迁移风格；跨表存在性、同租户约束和状态机由 Services 事务校验。
  • ch_audit_record 和 ch_event_checkin 为追加型记录，不提供软删除字段。
  • 商业事件、幂等记录和退款尝试同样不提供软删除。身份、哈希、来源、渠道和金额写入后不可覆盖；租约、状态、查询次数和最终结果只允许前向更新。新的渠道退款尝试必须追加新记录。
  • 所有带唯一索引的 slug、code 和业务编号都必须在写入前生成，数据库不提供空字符串默认值。
  • 一个会员只能有一个有效主展示角色，由事务同步 ch_member_role.is_primary 与 ch_tenant_member.primary_role_id；MySQL 5.7 不使用条件唯一索引。
  • 票种的 reserved_count 与 paid_count 是并发缓存，必须在锁内与报名状态一起更新，并可由报名表重算。
  • 每个新增 *.up.sql 必须同步新增同版本 *.verify.sql；校验应描述该迁移长期成立的后置条件，并允许后续迁移追加新列或新索引。

G1 会籍事实约束

  • ch_order_context.order_pk 绑定前允许 NULL，绑定后全库唯一；同一 CRMEB 订单不能落入两个租户或两个领域上下文。
  • ch_membership_term.state 只保存 granted、revoked、fully_refunded 三类事实；scheduled、active、expired 由 [effective_start_time,effective_end_time) 实时计算。
  • ch_tenant_member.tier、tier_expire_time 和 current term 是可重算投影，不得代替期限与效果流水。
  • ch_graduate_verification.current_slot 对当前申请写 1，历史申请写 NULL；利用 MySQL 多 NULL 唯一键阻止同会员并发产生两条当前申请。
  • ch_member_consent 和 ch_membership_term_effect 只追加，不软删除；前者禁止保存原始 IP/User-Agent，后者以 effect key/hash 检测重放冲突，同一 term 的 completion_id 跨 partial/full effect 类型只能入账一次。
