1. 验收结论

方向未漂移，G1-01E 本地闭环已完成：毕业认证通过的会员可创建 CRMEB 会籍订单；可信支付成功后，订单、OrderContext、inbox、term、grant effect 与会员等级在同库事务中一致提交；到期或全额退款后从期限事实重算并回落到 L2。
能力实现状态约束
支付完成接入StoreOrderSuccessServices 在根应用与 API 应用中绑定可信会籍适配器普通商品继续执行 CRMEB 原实现；会籍单先重读订单和 OrderContext，任一事实不一致即失败关闭
事件与权益原子写入 ch_commerce_event_inbox，创建唯一 term 与 grant effect同源事件同 hash 可重放，异 hash 冲突；事件、期限、效果和投影同事务提交
续费与升级同等级续费从该等级最后结束时间继续；更高等级立即生效会员行锁串行并发购买；期限采用半开区间 [start,end)
等级与到期从批准认证和有效 L3/L4 term 重算 tier、到期时间及 current term投影不是财务事实源；定时补扫只重算，不改写期限事实状态
全额退款可信完成事件追加 full-refund effect，term 转为 fully-refunded 并重算等级完成 ID 和效果键幂等；累计退款不得倒退或超过实付
我的会籍GET /chamber/v1/me/membership 已实现只返回当前认证用户在可信 tenant/channel 下的等级、期限和购买能力

2. 运行链路

CRMEB 支付回调 / 余额支付 / 零元完成
  -> GuardedStoreOrderSuccessServices
  -> 锁 eb_store_order + ch_order_context
  -> 校验 uid / order_no / unique / 金额 / 币种 / 虚拟类型 / 状态
  -> 更新 CRMEB paid 与 OrderContext payment fact
  -> 写唯一 commerce.order.completed.v1 inbox
  -> 锁会员行，创建唯一 membership term + grant effect
  -> 从全部有效期限重算 member projection
  -> inbox 标记 processed
  -> 同一 MySQL 事务提交

定时任务 MembershipOrderContextRepairJob 继续修复下单绑定缺口，并补消费可重试 inbox、重算到期或待生效期限。根 provider 对 HTTP、队列、timer 和 CLI 一致生效；API provider 显式重复关键绑定，避免多应用覆盖导致旁路。

3. 关键不变量

  • 会籍支付只能处理已绑定的单商品 CRMEB 虚拟订单；订单 unique 必须等于 OrderContext context number。
  • 订单实付、上下文应付/实付、事件金额和币种必须完全一致；支付完成后不得再接受取消或关闭状态。
  • 一个 OrderContext 只能创建一个 term；一个支付 event 只能创建一个 grant effect。
  • 同等级并发续费在会员行锁后重新查询最后期限，不依赖请求到达顺序，也不覆盖旧期限。
  • L4 全额退款或到期后，若仍有有效 L3 自动回落到 L3；否则批准认证会员回落 L2，认证撤销则回落 L1。
  • 原生管理端、客服和 OutAPI 发货/收货入口由 delivery 与 OutAPI 服务守卫拒绝会籍订单，防止虚拟会籍被原生履约状态机改写。
  • 事件载荷只保留最小商业事实，不写姓名、手机号、地址、OpenID 或证件信息。

5. 仍未完成的生产边界

本地权益闭环不等于真实资金联调：当前门禁通过服务层可信支付适配器验证，尚未配置正式微信 AppID、商户号、API v3 密钥、平台证书和公网回调域名。
  • 真实微信支付与退款通知的签名、重放、对账和异常补单仍需正式商户环境联调。
  • 原生会籍退款入口当前保持拒绝；全额退款消费者已验证，但正式退款申请、审核和 provider 完成事件生产器尚未交付。
  • 部分退款期限折算、按天补差价、自动续费、推荐奖励和退款冲正继续暂缓，等待财务规则确认。
  • 会员端会籍信息 API 已完成，正式视觉页面和支付结果页仍需后续前端切片。
  • 专业恶意软件扫描、生产对象存储、监控、告警、备份恢复和安全测试仍是上线硬门槛。
