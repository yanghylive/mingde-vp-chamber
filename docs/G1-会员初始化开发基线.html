2. 受保护请求顺序

POST /chamber/v1/me/bootstrap
  -> RequestTraceMiddleware
  -> ChamberCorsMiddleware
  -> CrmebAuthTokenMiddleware       # Auth：真实 CRMEB api Token
  -> TenantContextMiddleware        # Tenant：Host 映射或受信 HMAC
  -> MemberBootstrapController
  -> MemberBootstrapService         # 单数据库事务
顺序约束：Auth 必须先于 Tenant。业务服务只接受认证上下文中的 uid 和 TenantContext 中的 tenant/channel；请求正文只能携带 invite_code 与协议接受项。

3. 幂等身份与请求身份

客户端 Idempotency-Key 先做长度和字符集校验，但不直接作为数据库唯一身份。服务按规范化 JSON 计算两个不同摘要：

internal key = sha256-v1(
  trusted tenant_id,
  operation = bootstrapChamberMember,
  principal type = crmeb_user,
  authenticated uid,
  caller Idempotency-Key
)

request hash = SHA-256(
  trusted channel_id,
  normalized invite_code + consents
)
  • 同 tenant、同主体、同 Key、同请求返回已保存结果。
  • 同内部 Key 但请求哈希不同，返回 HTTP 409 idempotency_conflict。
  • 同一个客户端 Key 在不同租户会派生不同内部 Key，不共享会员或结果。
  • 重放成功结果前重新读取当前会员状态；历史 200 不能绕过后续退出或停用。

4. 事务与唯一性

lock/create ch_idempotency_record
  -> lock/create ch_tenant_member
  -> lock/create ch_member_profile
  -> resolve server consent documents
  -> append missing ch_member_consent events
  -> persist response snapshot + hash
  -> commit
事实必须保持
会员同一 tenant_id + uid 只有一个 member；同一 CRMEB uid 可在另一个租户拥有独立 member
资料同一 tenant_id + member_id 只有一个 profile；并发初始化不得创建孤儿或重复资料
协议同 member、同协议当前版本和正文哈希只需一条接受证据；重复 bootstrap 不追加相同接受事件
归因只有第一次初始化可写 first channel/referrer；当前渠道可随可信请求更新，首次归因不可变
