G0-06 · COMMERCE EVENT AUDIT · 2026-07-21

CRMEB 支付退款事件核验

基于锁定的 CRMEB-KY v6.0.0 源码，确认各支付/退款通道的真实事务、事件和幂等语义，并冻结 Chamber 统一交易事件契约。

项目首页 开发任务板 二开说明书 源码审计脚本 数据库契约

1. 结论

不能直接挂业务权益：CRMEB 的支付事件没有覆盖线下确认和 other_order，在线回调的“查 paid → 无条件更新 → 同步副作用”也不是原子幂等。它只能作为加速信号，最终以重读订单、事件收件箱唯一键和对账补偿为准。
退款成功名称不等于资金完成：admin_order_refund_success 在渠道退款请求未抛异常后立即发出，同时把本地订单写成已退款；源码没有退款回调消费或业务层 queryRefund 对账。外部渠道只能先记 processing，查询或人工财务确认终态后才能冲正权益。
  • G0-06 建立事实事件、幂等记录、退款尝试和源码兼容审计，不实现会籍或活动副作用。
  • G1/G2 只消费统一的 commerce.order.completed.v1，不得各写一套支付回调。
  • 退款申请只冻结；取消只恢复冻结；processing 不撤销权益；completed 才生成最终冲正。

2. 支付链路覆盖

链路真实入口统一事件覆盖Chamber 策略
商品在线支付PayNotifyServices → StoreOrderSuccessServices::paySuccess有 OrderPaySuccessListener，但预查与写入分离，副作用非原子重读订单核对 paid、金额、租户上下文；写唯一 inbox；定时补扫
商品余额/零元YuePayServices / zeroYuanPayment进入标准 paySuccess；零元被记作 yue现金支付与零元完成用 completion_kind 区分
商品线下确认OrderOfflineServices::orderOffline绕过 OrderPaySuccessListener，副作用集合也不同仅人工确认后由订单补扫产生统一完成事件
CRMEB 会员订单OtherOrderServices::paySuccess不发统一支付事件，且先延长会员再写 paid商会 L3/L4 不复用原生会员卡语义；使用虚拟商品 + OrderContext

主要源码证据：app/services/pay/PayNotifyServices.php、app/services/order/StoreOrderSuccessServices.php、app/services/pay/OrderOfflineServices.php、app/services/order/OtherOrderServices.php。

3. 退款完成能力

渠道发起后本地行为最终态能力允许完成条件
微信 V3同步请求成功后立即写 refund_status=2驱动有查询方法，业务层未调用；无退款通知入口查询返回 SUCCESS
微信 V2同上包装器引用的查询方法在当前 WechatService 中不存在补齐并验证查询适配后才可启用
支付宝同步接口 success 后立即写已退款SDK 有 queryRefund，业务层未调用查询确认退款金额和终态
通联同步接口 success 后立即写已退款queryRefund 是 TODO首发禁用自动完成，转人工财务确认
余额同一数据库事务加回余额并写流水可同步确认，但原流水没有业务唯一键Chamber 幂等键抢占成功且余额事务提交
线下没有资金退款分支，却仍可能写已退款与负流水系统无法确认真实到账上传凭证并人工确认

CRMEB 还会临时用“订单号 + 三位随机数”生成退款号但不持久化，网络超时后无法安全查询或重试；部分退款也会被立即标成全部退款。Chamber 必须先保存稳定退款尝试，再调用渠道。

4. 统一事实事件

事件触发条件允许副作用
commerce.order.completed.v1重读订单确认已支付，或零元业务完成G1/G2 激活会籍、报名、预约等；completion_kind=paid/zero_amount
commerce.refund.requested.v1售后申请已提交冻结履约、权益和待结算
commerce.refund.cancelled.v1未完成的退款申请已取消恢复被冻结状态；完成后的迟到取消必须拒绝，取消后的可信资金完成仍须接纳并重新冲正
commerce.refund.processing.v1CRMEB 标记已退款或支付机构受理记录与查询，不做最终冲正
commerce.refund.completed.v1余额事务提交、渠道查询成功或人工财务确认最终撤销/缩短权益并写负向账本
commerce.refund.failed.v1渠道确认失败/关闭，或人工驳回恢复冻结并告警

公共字段包含 event/source/source_event、Unix 秒时间、correlation ID、tenant/channel、order、uid、business/context、金额/币种、退款完成版本和 payload hash。事件 payload 禁止姓名、手机号、地址、证件号和 openid。

5. 持久化与幂等

表用途关键约束
ch_commerce_event_inbox持久化事实事件及处理状态(tenant_id,source,event_type,source_event_id) 唯一；同 hash 去重，不同 hash 冲突
ch_idempotency_record业务副作用租约、结果重放和失败记录(tenant_id,idempotency_key) 唯一；数据库约束承担并发仲裁
ch_refund_attempt持久退款号、渠道状态、查询重试和最终确认退款号唯一；每次部分退款独立 attempt/completion ID
 
支付权益：order_paid:{order_pk}:{business_type}
退款效果：refund:{refund_pk}:{completion_id}:{ledger_type}
事件身份：sha256(tenant_id + source + event_type + source_event_id + schema_version)

事件处理器必须先落 inbox/幂等记录，再执行副作用；同一来源事件键不同 payload 不允许覆盖。退款效果按 completion_id 和金额、订单、业务上下文等金融事实指纹去重，因此同一资金完成的不同查询观测不会重复冲正，而相同 completion_id 对应不同金额时必须冲突。事件丢失由订单/退款对账补发。
