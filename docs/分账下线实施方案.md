# 分账下线实施方案（改为单方收款）

> 文档版本：v1.0　　编制日期：2026-10-04　　适用分支：`main`
> 关联决策：**不再做三方 4:4:2 分账，资金由一家主体直接收款；汇付（Huifu）保留为支付通道。**
> 关联文档：[核心能力质量升级开发指导](./CORE-CAPABILITY-QUALITY-UPGRADE.md)（其阶段 1「结算与真实打款安全重构」随本方案作废）、[汇付三方分账接入方案](./HUIFU-三方分账接入方案.md)（废弃）、[汇付分账 Adapter 验收清单](./HUIFU-分账adapter-验收清单.md)（废弃）

## 1. 背景与决策

### 1.1 已建成的分账系统（将被移除）

| 提交 | 内容 |
|---|---|
| `f6585ee` | 分账骨架：规则引擎 + 结算单 + T+1 + 下期抵扣 |
| `77149a2` | T+1 结算接入 crontab 定时任务 |
| `0706833` | 真实通道对接（商家转账 / 微信分账 / 对公银行） |

| `6fc5af0` | 汇付三方分账底座 PR-01（配置/传输/签名骨架） |

### 1.2 关键事实（决定下线成本很低）

- `SettlementService` 的**唯一调用方**是 `SettlementAdminController`、`SettlementSettleJob`、`tests/settlement_state_machine_db_run.php` 三处。
- 支付完成链路（`MembershipPaymentCompletionService`、`EventRegistrationCommerceProjection`、`CrmebEventRefundGateway`）**不会自动生成结算单**，结算单只能由管理员手动传 `order_amount` 创建。
- 因此：删除结算子系统 **不影响支付、退款、会员权益、活动报名的任何主链路**。
- `frontend/custom` 全仓 grep `settlement` **零命中**，没有管理端/小程序页面需要改。

### 1.3 决策记录

| 项 | 决定 |
|---|---|
| 分账（结算单/明细/打款/抵扣/规则） | **删除** |
| 汇付 `HuifuConfig` / `HuifuHttpClient` / `HuifuSigner` | **保留**，作为后续汇付支付通道的预留底座 |
| `HuifuPaymentChannel` / `HuifuClient` 支付链路 | 目前**不存在**，属后续独立工作包（见 §9） |
| 收款主体 | 一家主体直接收款，走既有微信支付 APIv3 直连 + 小程序虚拟支付 |

## 4. 数据库处理（关键约束）

### 4.1 硬约束

1. **已应用迁移的 checksum 不可变**（`manage-local-database.sh` 会 `fail "Applied migration checksum changed"`）→ 不允许修改 `202608160011` / `202608160013` 的既有文件，只能**整套删除 + 新增 contract 迁移**。
2. **up/verify 必须成对**（`preflight_migrations` 要求每个 `*.up.sql` 有非空 `*.verify.sql`，且 verify 不能成为孤儿）→ 两套迁移必须 `up/verify/down` 共 6 个文件一起删。
3. 旧结算迁移的 `verify.sql` 断言 5 张表**存在**，若只删表不删 verify，`verify` 全量复验会失败。

### 4.2 方案

删除 §2.1 中两套迁移（6 文件），新增一套 contract 迁移：

```
backend/custom/database/migrations/202610040001_drop_chamber_settlement.up.sql
backend/custom/database/migrations/202610040001_drop_chamber_settlement.verify.sql
backend/custom/database/migrations/202610040001_drop_chamber_settlement.down.sql
```

- `up.sql`：`DROP TABLE IF EXISTS` × 5（`ch_settlement_rule`、`ch_settlement`、`ch_settlement_detail`、`ch_payout_record`、`ch_settlement_balance`），并在 `ch_schema_migration` 中保留旧版本行（无副作用：`verify_migrations` 只遍历现存文件）。
- `verify.sql`：断言 5 张表 `NOT EXISTS`（沿用现有 `SELECT 'xxx.absent' AS check_name ... PASS/FAIL` 风格，`grep -Eq 'FAIL'` 即失败）。
- `down.sql`：重建 5 张表结构（内容取自原 `202608160011_settlement.up.sql`），用于回滚。

### 4.3 为什么删表不会打挂既有门禁

- `check-g0-baseline.sh`：`database_tables -ge 174`、`chamber_tables -ge 17`（**下限**断言）
- `check-g1-membership-baseline.sh`：`database_tables -ge 180`、`chamber_tables -ge 23`（**下限**断言）
- 删除后为 **182 张表 / 25 张 ch_ 表**，仍满足 ≥180 / ≥23 ✅
- `manage-local-database.sh` 无总量断言 ✅
