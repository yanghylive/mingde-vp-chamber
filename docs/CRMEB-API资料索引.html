1. 结论

CRMEB 有 API 文档，但不是一份可无条件信任的 v6 OpenAPI 文件。当前可用资料由四部分组成：官方帮助站及 Apifox、仓库内开发文档、应用路由源码、后台 OutAPI 接口文档模块。

优先级：路由 + 中间件 + Controller + Services 是唯一执行真相；Apifox 用于快速理解和联调；仓库内 AI 生成的简要 API 文档只能当搜索线索。

4. 鉴权与对外接口

4.1 OutAPI 请求链路

POST /outapi/access_token  -- appid + appsecret --> access token
API request               -- Authori-zation: Bearer <token>
AuthTokenMiddleware       -- parseToken + account status
OutInterfaceServices      -- verify method/path against account rules
Controller / Services     -- execute business operation

鉴权头名从 CRMEB 配置 cookie.token_name 读取，默认为源码中的 Authori-zation。二开不应擅自改为标准 Authorization 而不同步全端。

4.2 内建文档管理

后台路由 system_out_interface/list|save|info|edit_name|del 对应 SystemOutAccount 控制器，数据由 OutInterfaceServices 维护。它保存请求参数、返回参数、示例和错误码，但并不会扫描全部用户端/管理端路由生成 OpenAPI。

MCP 注意：v6.0.0 outapi 中还有独立 POST mcp 路由，源码注释说明其支持 appid + appsecret 且不经 Token 中间件。上线前必须单独做权限、重放、限流和日志审计；非必需时应关闭或在网关拦截。

5. 本项目 API 治理

  • 新增用户端契约使用 /chamber/v1，管理端使用 /chamber/admin/v1，不与上游 v1/v2 路由混写。
  • 以项目管理的 OpenAPI 3.1 文件作为二开接口契约，测试环境自动发布 HTML 文档。
  • 每个接口必须登记需求 ID、租户数据范围、主体权限、幂等方式、业务错误码和审计事件。
  • CRMEB 上游升级后，先生成路由 diff，再对 Apifox 和项目 OpenAPI 执行契约回归。
  • 不将仓库内原始 Apifox 链接当作可写管理账号；项目自建文档空间必须由项目组保管。
