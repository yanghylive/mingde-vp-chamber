01 / CONCLUSION

结论与技术决策

CRMEB v6.0.0 可以承担账号、商品、订单、支付、退款、核销、客服、分销和后台权限，但不能直接等同于毕业生商会业务。二开必须以“复用交易底座、重建商会领域”为原则。

14,298官方仓库文件数
157安装 SQL 数据表
419 / 958移动 API / 管理 API 路由定义
854UniApp 与管理端 Vue 页面

1.1 已确定的架构决策

  • CRMEB 作为唯一交易主系统，不引入第二套商城或会员主库。
  • 官方源码以 Git 子模块固定版本，不直接在子模块中提交业务代码。
  • 业务二开采用父仓库 overlay，构建时叠加到 CRMEB 干净工作副本。
  • L1-L4 不复用 eb_user.level，该字段属于经验成长等级。
  • 渠道双壳使用新租户领域，不把 CRMEB 事业部/分销代理当作数据租户。
  • 活动不复用 eb_store_activity，该表服务于秒杀活动。
  • AI 网关独立部署，只通过受控 API 操作 CRMEB，不直接写业务数据库。
  • 所有支付、积分、贡献值、退款和分账使用追加式账本与冲正。
核心警告：类名“会员、好友、活动、事业部”与 PRD 用词相似，但实际语义不同。AI 编码前必须查阅本说明书的能力矩阵，禁止仅根据文件名判断可复用性。

06 / SEMANTIC GAPS

高风险误用点与业务缺口

付费会员不等于 L1-L4

eb_member_ship 可卖时长卡，但 eb_user.is_money_level 只表示付费来源，无法表达每个租户的 L3/L4 和历史变更。

用户等级不等于会籍

eb_user.level 由经验值和折扣驱动。把它用于付费等级会导致签到、消费和后台调级改变会籍。

好友记录不等于社交关系

eb_user_friends 没有申请状态、处理人、拒绝、拉黑和双向唯一约束，当前写入发生在推荐绑定流程。

营销活动不等于线下活动

eb_store_activity 管理秒杀商品时间段，不支持地点、地图、嘉宾、票种、资格、报名和签到。

事业部不等于租户

事业部主要服务分销层级，订单、商品、会员 API 没有强制事业部过滤，不能作为双品牌的数据隔离边界。

虚拟卡密不等于服务履约

课程、咨询和陪跑需要档期、参与人、会议链接、核销、交付凭证和争议处理，不能只发一组卡密。

9.1 不变量

  • 所有 ch_* 私域表必须含 tenant_id，后台查询必须同时受管理员数据范围限制。
  • 任何余额类字段必须能由账本重放验证，禁止只改余额不写账。
  • 业务关联 CRMEB 订单时保存数字主键和业务订单号，不能只保存展示字符串。
  • 订单、会籍、分账和权益保存下单时快照，配置修改不得改变历史订单。
  • 软删除用于内容；账本、支付、退款、审核和安全日志禁止物理删除。

10 / MEMBERSHIP & RELATIONSHIP

会员、会籍、积分与关系改造

10.1 会籍实现

CRMEB 原生付费会员最终写入全局 eb_user.is_money_level 和 overdue_time，不能表达双租户会籍。因此采用“CRMEB 虚拟会籍商品 + 自定义会籍期限”模式：

  1. L3/L4 各自对应租户下的虚拟商品 SKU，复用商品、订单、微信支付和退款。
  2. OrderPaySuccessListener 识别 ch_order_context.business_type=membership。
  3. 事务内创建或延长 ch_membership_term，刷新 ch_tenant_member.tier。
  4. 退款监听器按权益使用情况撤销或缩短会籍，并生成冲正记录。
  5. 到期 Job 将用户降至 L2，不删除积分、贡献值、好友和订单。

10.2 积分与贡献值

资产来源消费CRMEB 复用
租户积分活动、邀请、购买、运营发放活动票、商品、AI 配额复用订单抵扣和退款算法，存储改为 ch_point_*
贡献值教练、助教、分享、签到、邀请不可消费不复用 eb_user.exp，新增独立账本
推广佣金商品与会籍推广提现/结算复用 CRMEB brokerage，和积分严格分开

10.3 好友状态机

PENDING ──accept──▶ ACCEPTED
   │                    │
   ├──reject──▶ REJECTED│
   ├──cancel──▶ CANCELED│
   └──timeout──▶ EXPIRED│

任何状态 ──block──▶ BLOCKED（阻断目录可见性与再次申请）

CRMEB 的 eb_user_friends 不作为新好友系统事实来源。历史记录如需保留，只能通过一次性迁移并标记 source=legacy_referral。

11 / EVENT

活动、报名、票务与签到

11.1 复用策略

  • 活动内容：新建 ch_event，不用 CRMEB 秒杀活动表。
  • 票种：每个收费票种映射为 CRMEB 虚拟商品，免费票也生成零元订单/报名记录。
  • 支付退款：复用 CRMEB 订单、收银台、支付回调和退款。
  • 核销：复用核销码、核销员和防重复模式，但新建活动签到令牌与签到记录。
  • 通知：复用 NoticeListener、队列与模板消息，增加活动模板。

11.2 报名事务

1. 读取 TenantContext 与活动配置
2. 校验 L1-L4、人物角色、积分、渠道、时间窗
3. 获取 event_ticket 分布式锁
4. 检查 paid + reserved 是否小于容量
5. 创建 CRMEB 购物车/订单与 ch_order_context
6. 创建 registration=PENDING_PAYMENT 并占用名额
7. 支付成功监听器更新 PAID；超时 Job 释放名额
8. 退款成功监听器更新 REFUNDED 并释放/保留名额

11.3 签到安全

  • 二维码内容只包含短期随机 Token，不直接暴露活动 ID 和用户 ID。
  • Token 带活动、票种、过期时间和签名；服务端再次验证报名状态。
  • (event_id, uid) 唯一，重复请求返回原签到结果。
  • 人工补签必须写审核人、原因、时间和原报名状态。
  • 积分和贡献值发放使用签到 ID 作为幂等业务键。

12 / COMMERCE

商城、会员上架、履约与分账

12.1 商品类型扩展

不修改 CRMEB SPU/SKU 主结构，使用 ch_product_scope.business_type 扩展业务类型：

12.2 会员上架流程

DRAFT → SUBMITTED → IN_REVIEW → APPROVED → PUBLISHED
  ▲          │             │          │           │
  └─RETURNED─┘             └─REJECTED─┘           └─SUSPENDED

开源版不是多商户平台。L2+ 用户提交的是 ch_product_submission，审核通过后由平台服务账号创建 eb_store_product，并在 ch_product_scope 记录 owner_uid、tenant_id 和结算规则。用户不能直接获得 CRMEB 商品管理后台权限。

12.3 分账台账

  1. 下单时冻结平台、渠道、服务方、推荐人的比例与金额快照。
  2. 支付成功只记“待结算”，不得立即提现。
  3. 履约确认或售后期结束后转为“可结算”。
  4. 退款按原规则生成负向账本，不修改历史记录。
  5. 首发人工结算导出；微信自动分账开通后由 Job 执行并回写渠道单号。

17 / SECURITY

租户隔离、权限和隐私

17.1 TenantContext

  1. 从已签名渠道链接、小程序配置或域名解析 tenant/channel。
  2. 中间件验证租户状态、用户关系和管理员数据范围。
  3. 把 TenantContext 注入 Request/Container，业务服务不自行读取前端 tenant_id。
  4. Dao 查询必须通过 tenant-aware 基类或显式条件；缺少条件时测试失败。
  5. 跨租户共享资源使用显式 scope 表，不使用 tenant_id=0 的隐含约定。

17.2 权限矩阵

主体可见数据可执行操作
L1 游客公开活动、大咖、AI 工具登录、申请认证、购买会籍
L2+ 会员本租户会员目录和会员内容好友、活动、上架申请、购买
导师/教练/领袖本人主页、档期、订单编辑资料、管理档期、确认履约
渠道运营本渠道会员、活动、商品、订单审核与运营，不可改平台配置
财务订单、退款、分账和导出对账、结算、冻结
超级管理员全平台租户配置、跨租户共享与审计

17.3 敏感数据

  • 毕业证明、身份证明、手机号和咨询主题属于受限字段，默认不进入 AI 上下文。
  • 对象存储使用私有桶和短期签名 URL，数据库只保存对象键。
  • 日志中屏蔽 Token、手机号、支付参数、证明材料 URL 和模型 API Key。
  • 知识库入库前记录授权，删除时同步删除对象、索引与缓存。

20 / UPSTREAM UPGRADE

CRMEB 上游升级策略

  1. 创建 chore/crmeb-upgrade-x.y.z 分支。
  2. 读取官方 release、许可证和安装 SQL 差异。
  3. 更新子模块指针，不在原分支直接拉 master。
  4. 在全新构建目录应用 overlay，记录冲突和废弃 API。
  5. 执行迁移 dry-run、PHP 测试、API 回归和五条 E2E。
  6. staging 运行至少 3 天，完成支付/退款/签到演练。
  7. 批准后合并，并更新本说明书的源码基线。
禁止使用 CRMEB 后台在线升级覆盖生产代码。在线升级会绕过父仓库、overlay、代码审查和可重复构建，导致生产状态无法从 Git 还原。

22 / AI CODING RULES

AI 编码与代码审查规则

后续 AI 开发必须把以下规则作为仓库级约束：

  • 修改前先定位 CRMEB v6.0.0 的同类 Controller/Services/Dao/Model，列出复用点。
  • 不得直接修改 backend/crmeb；所有变更进入 overlay 或我方独立服务。
  • 不得把 eb_user.level、is_money_level、store_activity、division 当作 PRD 同名领域。
  • Controller 不直接操作数据库；跨表写入必须在 Services 事务内完成。
  • 每个私域查询明确 tenant_id；每个写操作声明权限、幂等键和审计事件。
  • 金额只使用字符串 decimal 与 BCMath；时间统一存 Unix 秒并明确时区。
  • 支付、退款、积分、贡献和分账必须先写测试，再写实现。
  • 新增 API 同时提交路由、验证器、权限菜单、错误码和 HTML 文档更新。
  • 数据库迁移只能追加，不直接编辑 CRMEB 安装 SQL。
  • 任何真实会员资料、会议纪要和密钥不得上传到外部模型。

22.1 Definition of Done

  • 需求 ID、代码、测试和验收截图/日志可相互追踪。
  • 单元、API、E2E 和租户越权测试通过。
  • 不存在子模块未提交修改和未登记依赖。
  • 迁移可在空库与现有测试库成功执行。
  • 监控、日志、告警、回滚和运维说明已更新。
  • 产品与技术负责人共同验收。
开发入口：先阅读 PRD v2.0 确认业务需求，再使用本文确定复用策略和代码边界。两份文档发生冲突时，业务行为以 PRD 为准，技术实现以本文为准，并通过变更评审消除冲突。
